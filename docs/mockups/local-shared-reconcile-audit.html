02 · LOCAL / SHARED

A container claim and a unit decision answer different questions

A file claim answers may SetForge reconcile this container? A stable unit classification answers may these bytes flow back to shared configuration? Neither implies the other. Mixed files can therefore contain confirmed SHARED units beside LOCAL, SHARED_DRAFTED, and PENDING units without accidental promotion.

Failure mode before hardening

tracked: team-setting=v1
live:    team-setting=v2 + secret-path

capture #1: keep locally, but refresh identity
capture #2: identity matches → silently publish

Current contract

changed SHARED identity → confirmation required
LOCAL / PENDING         → never promoted
SHARED_DRAFTED          → publish sanitized draft
missing/corrupt state   → preserve and refuse mutation

Stable typed unit identities replace collision-prone positional anchors. Participation is durable, so a temporarily unclassifiable file cannot fall back to whole-file capture. Capture locking, pruning, and recovery preserve the index-last publication boundary.

04 · Existing tools and state

Presence is evidence, not ownership

SetForge reports an existing resource as present and unowned. An explicit metadata-only adoption can then record a typed identity, owner, declaration, provenance, fingerprint, authority, generation, and history. It does not reinstall or rewrite the resource.

Adopt

Revalidate the frozen observation under locks and publish a claim with compare-and-swap semantics.

Release or transfer

Retain history and tombstones; refuse stale generations, competing owners, and changed fingerprints.

Change or remove

Require a current management grant and a separate operation. Matching bytes alone never bootstrap destructive authority.

This contract now covers typed capabilities, generated resources, directory trees, package provenance, and platform-specific release assets while preserving legacy receipts as non-destructive, unverified history.

06 · Remaining boundary

One optimization is intentionally deferred

Deferred, not missing: finer per-file Docker-daemon xdist grouping is scheduled for a later v0.3.x pass. The current prebuild and scheduling model is correct and predictable; the deferred work targets additional parallel throughput, not a correctness hole.
